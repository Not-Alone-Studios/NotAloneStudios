A valuation report is not final when it is typed. It is final only when the valuer has reviewed it, approved it, and the office can find the final file later.

This sounds obvious, but it is the stage where a lot of offices lose visibility. A draft exists in someone's Word file. Is it done? Is it waiting for the valuer? Did the correction get made? Was it actually submitted? In many offices the only way to answer these questions is to ask the person handling it — and if that person is out, the status is simply unknown.

This page explains how Maulya is being built to help track report preparation, approval, and final files, while keeping professional valuation judgment where it belongs: with the valuer.

## Why report preparation needs workflow visibility

A bank valuation report passes through several hands — office staff who assemble inputs, the valuer who reviews and approves, sometimes a junior who makes corrections. Between those hands, work waits. And waiting work is exactly what tends to go invisible.

Without visibility, two failures repeat. Reports sit longer than anyone realises, because nobody can see that a draft has been "ready for review" for three days. And after submission, the final file gets lost, because there was never a clear place that held the approved version.

The fix isn't more pressure on staff. It is being able to see, at a glance, where each report actually stands.

## Stages Maulya is being built to support

Maulya is being built to help offices track a report through its stages, so the status of each assignment is visible without a phone call. Depending on the office workflow, those stages include:

- **Inputs pending** — still waiting on details or evidence
- **Draft preparation** — the report is being assembled
- **Draft ready for review** — handed to the valuer
- **Correction requested** — the valuer has asked for changes
- **Corrected draft** — changes made, back for review
- **Valuer approved** — the valuer has signed off
- **Final report uploaded / stored** — the approved file is saved in one place
- **Submitted or closed** — where applicable to the office's process

The value isn't the labels themselves. It is that anyone in the office can see whether a report is moving or stuck, and where.

## What office staff need to see

For the people preparing reports, useful visibility means having, against each assignment: the intake details, the site evidence, the document status, the valuer's inputs, any correction notes, and the current approval status. When those sit together, staff aren't chasing information across chats to finish a draft.

## What the valuer needs to control

For the valuer, the report workflow should make review easier without taking over the judgment. That means a clear draft to review, the evidence and photos behind it, the valuation inputs, visibility into what corrections were requested and whether they were made, and — importantly — final approval control. The intended workflow is that approval remains a clear valuer-controlled step.

This is the line Maulya is being built to respect: visibility for everyone, approval authority for the valuer.

## What Maulya does not do

The limits matter most on this page, because this is where overclaiming would be most damaging.

Maulya does not replace valuer review. A report reaching "draft ready" does not make it correct. The review is the valuer's, and the platform exists to support it, not substitute for it.

It does not automatically approve reports. Approval is a deliberate action by the valuer, not something the system does on its own.

It does not guarantee bank acceptance. Whether a bank accepts a report depends on the bank, the report, and the valuer's work — not on the tool used to track it.

It does not decide value, and it does not make a report compliant by itself. Maulya organises the workflow around the report. The professional content of the report, and responsibility for it, stay with the valuer.

## Why final file storage matters

The report's life doesn't end at submission. Queries come back. Old references are needed. A similar property in the same locality comes up a year later and the earlier report would have been useful — if anyone could find it.

When the approved final file is stored in one place, tied to its assignment, it stays retrievable. When it lives in one person's laptop folder named "final final v3," it doesn't. Maulya is being built so the approved version can have a clear home, not so that it disappears into someone's downloads.

Maulya's report workflow is being designed to make report status visible — without taking professional judgment away from the valuer.

## FAQs

**Q1. Does Maulya write the valuation report automatically?**
No. Maulya is being built to track the report's preparation and approval status and to keep the related inputs and evidence together. The professional content of the report is the valuer's work.

**Q2. Can a report be approved in Maulya without the valuer?**
No. Approval is intended to be a deliberate action by the valuer. The workflow is being designed so a report does not move to "approved" on its own.

**Q3. Does Maulya guarantee the bank will accept the report?**
No. Acceptance depends on the bank, the report, and the valuer's work. Maulya helps the office see and manage the workflow — it makes no promise about a bank's decision.

**Q4. Why does Maulya emphasise final file storage?**
Because the file is needed again — for queries, old references, or a later assignment in the same area. Keeping the approved version in one place, linked to its assignment, is what keeps it retrievable instead of lost in a personal folder.

**Q5. Is this report workflow live in Maulya today?**
Maulya's MVP is still under development. This page describes how the report-tracking workflow is being designed to work, rather than claiming every stage is already available.
