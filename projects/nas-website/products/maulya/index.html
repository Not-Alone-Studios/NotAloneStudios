How Maulya is built.

Maulya keeps each bank valuation in one file, from the day it comes in to the day it is paid. This page is about the engineering underneath. For what it does in a valuer’s office, maulya.in tells the story.

Seven principles

Why a firm can trust it.

A valuation office hands Maulya its files, its photos and its reports. These are the rules the code keeps so that trust is earned.

01

Each firm’s data, kept apart

Every request carries its firm, and the database draws the same line itself, with row-level rules. The server won’t start on a database login that could step past them, and work that spans firms runs one firm at a time.

02

The server owns every file

A file is always in one of seven states, with one next step. Both are worked out on the server: the file’s page and the queue ask the same code, so they can’t say different things.

03

Who did what, and when

Actions on a file are written to an audit trail: who did it, when, and what it was before and after. Records about money and access are kept longer than routine ones.

04

Photos first, signal later

On the phone, each site photo is kept the moment it’s taken, then sent by itself when there’s signal, trying again after a failure. However often it’s sent, it arrives as one photo.

05

Reports in the lender’s format

Reports are filled into the lender’s own template. A draft carries a DRAFT mark and can be remade as the figures change; a final is issued once and frozen.

06

The owner decides who may do what

Person by person: who may change the figures, who may see money, who may finalise. The server checks each switch on every request; the screens only show what it allows.

07

Checked, backed up, reversible

Every change runs the automated checks before it’s merged. A release goes out only after they pass, takes a fresh backup first, and rolls itself back if the health check fails. Database changes follow a written runbook.

One track for every file

Seven states, one next step.

The office and the site engineer see the same track. Each step names who acts next; the file moves on only when the server agrees it can.

  1. Not startedA new file, made once
  2. At siteThe visit, on the phone
  3. Waiting at deskThe visit is checked
  4. At deskThe report is made
  5. With the valuerApproved, or sent back
  6. Ready to goPrinted, signed, handed over
  7. DeliveredPaid, and kept

The shape of the system

Screens that show, a server that decides.

Keeping the rules in one place is what lets the desk, the phone and the reports agree. The screens never work out a file’s state or a person’s rights for themselves.

  1. The screensThe office works at a desk in the browser; site engineers work on the phone.
  2. The serverWritten in Python. It owns each file’s state and next step, checks every permission, keeps the audit trail and makes the reports.
  3. The databasePostgreSQL, with row-level rules that keep each firm’s rows to that firm.
  4. ReleasesAutomated checks on every change; one release command, with a backup before and an automatic way back.
